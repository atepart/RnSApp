# AGENTS.md

Этот файл задаёт обязательные правила работы AI-агентов с репозиторием `RnSApp`.
Правила действуют для всего проекта. Если в подкаталоге появится свой `AGENTS.md`,
он может уточнять эти правила только для файлов внутри этого подкаталога.

## 1. Базовые правила командной строки

- **Каждая shell-команда без исключений начинается с `rtk`.** Это относится к
  чтению файлов, поиску, Git, `uv`, линтерам, тестам, запуску приложения и сборке.
- В цепочке команд `rtk` ставится перед каждым отдельным сегментом:
  `rtk git status && rtk git diff`.
- Не запускать напрямую `python`, `python3`, `pip`, `pytest`, `ruff`, `black`,
  `isort`, `pre-commit`, `pyinstaller` и другие Python-инструменты.
- Python и все Python-инструменты запускать только через установленный `uv`,
  сохраняя обязательный префикс `rtk`:

  ```bash
  rtk uv run python main.py
  rtk uv run python -m unittest discover -s tests -p "test_*.py"
  rtk uv run ruff check .
  rtk uv run black --check .
  rtk uv run isort --check-only .
  rtk uv run pyinstaller RnSApp.spec
  ```

- Для первоначальной подготовки окружения использовать:

  ```bash
  rtk uv venv
  rtk uv pip install -r requirements.txt
  ```

- Если команда через `uv` не работает из-за sandbox, доступа к кэшу или сети,
  запросить нужное разрешение или явно сообщить о блокировке. Не обходить правило
  запуском системного Python.
- Для поиска предпочтительны `rtk grep` и `rtk find`, для чтения — `rtk read`,
  для Git — команды вида `rtk git ...`.

## 2. Что представляет собой проект

`RnSApp` — нативное desktop-приложение на PySide6 для расчёта Rn/S,
визуализации данных и импорта/экспорта XLSX.

- `domain/` — модели, ошибки, константы, порты и чистая предметная логика.
- `application/` — прикладные расчёты, версия и координация сценариев.
- `infrastructure/` — XLSX, шаблоны, persistence, GitHub Releases и обновления.
- `ui/` — PySide6-интерфейс, таблицы, ячейки, графики и диалоги.
- `main.py` — composition root и точка запуска приложения.
- `assets/` — иконки и другие ресурсы приложения.
- `RnSApp.spec`, `build.sh`, `build.bat` — сборка дистрибутива.

Соблюдать направление зависимостей: предметная логика не должна зависеть от UI
или инфраструктуры. Новые вычисления по возможности размещать в `domain/` или
`application/`, а в UI оставлять отображение и обработку пользовательских
действий. Доступ к XLSX, сети и диску держать в `infrastructure/`.

Не редактировать вручную `.venv/`, `build/`, `dist/`, `.ruff_cache/`,
`__pycache__/` и другие сгенерированные файлы. Не менять и не перезаписывать
примерные `.xlsx`-файлы в корне, если этого прямо не требует задача. В тестах
использовать временные копии и временные каталоги.

## 3. Рабочий процесс для любой фичи или исправления

1. Прочитать связанные модули, `README.md`, актуальные тесты и проверить
   `rtk git status --short`. Не затирать и не включать в коммит чужие изменения.
2. До правки определить пользовательский сценарий и ожидаемый результат:
   какие данные вводятся, какая кнопка нажимается, что меняется в таблице,
   графике, XLSX или диалоге.
3. Сделать минимальное связное изменение без попутного рефакторинга, который не
   нужен задаче.
4. Добавить или обновить автоматические тесты для изменённой логики. Исправление
   бага должно по возможности включать регрессионный тест, который падал до
   исправления.
5. Запустить релевантные автоматические проверки.
6. **Реально запустить приложение**, пройти пользовательский сценарий мышью и
   клавиатурой, проверить результат глазами и сделать скриншоты.
7. Проверить итоговый diff и только после успешных автоматических и ручных
   проверок создать один сфокусированный коммит.

Не считать задачу выполненной только потому, что код импортируется или unit-тест
прошёл. Для UI-фичи обязательна проверка в запущенном приложении.

## 4. Обязательные рабочие документы

Состояние проекта нужно поддерживать не только в коде, но и в трёх файлах:

- `docs/workplan.md` — текущий план работы: активная задача, конкретные шаги,
  их статус, проверки и ближайшее следующее действие;
- `docs/bugs.md` — подтверждённые дефекты с шагами воспроизведения, ожидаемым и
  фактическим результатом, серьёзностью и статусом исправления;
- `docs/backlog.md` — будущие фичи, улучшения и технический долг, которые не
  входят в текущую задачу.

Правила ведения документов:

1. В начале каждой задачи прочитать все три файла и сверить их с запросом
   пользователя и текущим состоянием кода.
2. До изменения кода добавить текущую задачу и план проверки в
   `docs/workplan.md`. Во время работы сразу отмечать завершённые шаги и новые
   блокеры; план должен отражать реальное состояние, а не первоначальные догадки.
3. Любой воспроизводимый баг записать в `docs/bugs.md`. Если баг исправляется в
   текущей задаче, связать запись с пунктом workplan, добавить регрессионную
   проверку и после проверки сменить статус на `Исправлен`.
4. Идеи и работы вне согласованного scope не реализовывать попутно, а записывать
   в `docs/backlog.md` с причиной и приоритетом.
5. Не дублировать одну задачу в нескольких местах: workplan описывает текущую
   работу, bugs — сам дефект, backlog — ещё не взятую в работу идею. Использовать
   ссылки между записями.
6. Для новых записей указывать дату в формате `YYYY-MM-DD`, короткий стабильный
   идентификатор и один из статусов, заданных ниже.
7. Перед коммитом обновить все затронутые документы: отметить фактически
   выполненные тесты и ручную UI-проверку, убрать устаревшее «в работе», указать
   оставшиеся ограничения. Документация входит в тот же сфокусированный коммит,
   что и соответствующее изменение кода.
8. После успешной проверки перед коммитом перенести задачу в раздел недавно
   завершённых в `docs/workplan.md`. После коммита сообщить его hash пользователю.
   Не объявлять пункт завершённым до реального прохождения обязательных проверок.

Не превращать эти файлы в журнал рассуждений. Записи должны быть короткими,
проверяемыми и полезными следующему агенту.

### Формат `docs/workplan.md`

Разрешённые статусы задачи и шагов: `Запланирован`, `В работе`,
`Заблокирован`, `Выполнен`.

Для активной задачи обязательно указывать:

- идентификатор вида `WORK-YYYYMMDD-N`, дату, статус и пользовательскую цель;
- связи с `BUG-*` или `BACKLOG-*`, scope и то, что осознанно не входит в scope;
- короткий checklist конкретных шагов с актуальными статусами;
- результаты автоматических тестов и ручного UI-сценария;
- пути к скриншотам, ограничения, блокеры и ближайшее следующее действие.

Структура записи:

```markdown
### WORK-YYYYMMDD-N — Короткое название

- Дата: YYYY-MM-DD
- Статус: В работе
- Цель: наблюдаемый пользовательский результат
- Связи: BUG-... / BACKLOG-... / нет
- Scope: изменяемые части проекта
- Не входит в scope: осознанные исключения

#### Шаги

- [ ] [Запланирован] Конкретный шаг
- [ ] [Запланирован] Автоматические тесты
- [ ] [Запланирован] Реальный UI-сценарий и скриншоты
- [ ] [Запланирован] Проверка diff и commit checklist

#### Проверки

- Автоматические: ещё не выполнены
- Ручной UI-сценарий: ещё не выполнен
- Скриншоты: ещё не созданы
- Ограничения/блокеры: нет
- Следующее действие: конкретный ближайший шаг
```

В самом `docs/workplan.md` хранить только реальные активные и недавно
завершённые задачи. Не копировать туда эти правила или шаблон.

### Формат `docs/bugs.md`

Статусы: `Новый`, `Подтверждён`, `В работе`, `Исправлен`,
`Не воспроизводится`, `Отклонён`. Серьёзность: `Критическая`, `Высокая`,
`Средняя`, `Низкая`.

Запись подтверждённого дефекта должна содержать:

```markdown
### BUG-YYYYMMDD-N — Короткое описание

- Дата: YYYY-MM-DD
- Статус: Подтверждён
- Серьёзность: Средняя
- Компонент: domain / application / infrastructure / ui / build
- Связанная работа: WORK-... / нет
- Окружение: ОС, версия Python, способ запуска
- Предусловия: необходимые данные или состояние
- Шаги воспроизведения:
  1. Действие пользователя
  2. Следующее действие
- Фактический результат: что произошло
- Ожидаемый результат: что должно произойти
- Доказательства: лог и/или путь к скриншоту
- Регрессионный тест: путь к тесту / ещё не добавлен
```

После исправления перенести запись из открытых в исправленные, указать дату,
связанную работу и проведённые проверки. В самом `docs/bugs.md` хранить только
фактические дефекты и их состояние, без правил и шаблонов.

### Формат `docs/backlog.md`

Статусы: `К рассмотрению`, `Принято`, `Отложено`, `Взято в работу`,
`Отклонено`. Приоритеты: `P0`, `P1`, `P2`, `P3`, где `P0` — самый высокий.

Структура записи:

```markdown
### BACKLOG-YYYYMMDD-N — Короткое название

- Дата: YYYY-MM-DD
- Статус: К рассмотрению
- Приоритет: P2
- Компонент: domain / application / infrastructure / ui / build
- Пользовательская ценность: зачем это нужно
- Критерии готовности: наблюдаемый результат
- Причина отсрочки: почему не входит в текущую работу
- Зависимости/риски: нет
- Связанная работа: WORK-... / нет
```

Когда пункт берётся в работу, создать `WORK-*`, связать записи и изменить статус
на `Взято в работу`. В самом `docs/backlog.md` хранить только конкретные будущие
работы и их состояние, без правил и шаблонов.

## 5. Автоматические тесты

- Чистые расчёты и преобразования тестировать без запуска GUI.
- Для XLSX проверять round-trip во временном файле: запись, повторное чтение,
  значения, типы, пустые ячейки и ошибки входных данных. Не портить реальные
  файлы пользователя.
- Сетевые сценарии и обновления тестировать с mock/fake-ответами. Не скачивать
  релизы и не зависеть от доступности GitHub в обычном тестовом прогоне.
- Для UI-тестов создавать один `QApplication`, имитировать действия пользователя
  и проверять видимое состояние виджетов и данные модели.
- Проверять не только happy path, но также пустой ввод, некорректные числа,
  отмену диалога, повторное нажатие и сохранение/повторное открытие данных.
- Новые автоматические тесты размещать в `tests/`. Имена: `test_*.py`.
- Корневые `test_ui.py`, `test_thread.py`, `test_dl.py`, `test_dl2.py` сейчас
  являются ручными диагностическими скриптами, некоторые открывают GUI или
  обращаются к сети. Не считать их полноценным pytest-набором и не запускать все
  без анализа. Запускать только явно релевантный скрипт, например:

  ```bash
  rtk uv run python test_ui.py
  ```

Минимальный автоматический прогон для нового каталога `tests/`:

```bash
rtk uv run python -m unittest discover -s tests -p "test_*.py"
```

Если в рамках задачи добавлен и настроен pytest, использовать:

```bash
rtk uv run pytest tests/
```

## 6. Обязательная реальная проверка интерфейса

Запускать приложение из исходников так:

```bash
rtk uv run python main.py
```

Проверка должна происходить в обычном графическом режиме, не только с
`QT_QPA_PLATFORM=offscreen`. Агент обязан открыть окно и реально пройти
затронутый сценарий. Для типичной фичи проверить:

- приложение стартует без traceback, главное окно полностью отображается;
- элементы не обрезаны, не перекрываются и не выходят за границы окна;
- подписи, состояния кнопок, таблицы, доки, диалоги и графики выглядят корректно;
- ввести тестовые данные и нажать затронутые кнопки, а не только осмотреть окно;
- для расчёта — нажать «Рассчитать» и сверить таблицу, средние значения,
  подсветку ошибок и обновление графика;
- для записи ячейки — нажать «Записать», проверить имя и значения, затем
  релевантные пункты контекстного меню;
- для XLSX/шаблонов — выполнить сохранение во временный файл, открыть его обратно
  и сравнить восстановленные данные;
- проверить очистку, отмену диалогов, повторное действие и сообщения об ошибках;
- после сценария убедиться, что в терминале нет новых исключений и критических
  предупреждений.

Использовать доступные средства GUI-автоматизации для кликов, ввода и снимков
экрана. Скриншоты делать как минимум после запуска и после результата изменённого
сценария; при визуальном изменении полезен также снимок до правки. Скриншот должен
показывать именно проверяемое состояние, а не пустой рабочий стол.

Скриншоты и временные XLSX хранить вне исходников, например в отдельном временном
каталоге. Не добавлять их в Git, если пользователь явно не попросил приложить
тестовые артефакты. В итоговом отчёте перечислить пройденные действия и указать
пути к скриншотам. Если среда физически не позволяет открыть GUI, нажать кнопки
или сделать снимок, честно отметить непроведённую проверку; нельзя заявлять, что
ручной тест пройден.

## 7. Проверка перед коммитом

Перед каждым коммитом обязательно выполнить применимые команды:

```bash
rtk uv run ruff check .
rtk uv run black --check .
rtk uv run isort --check-only .
rtk uv run python -m unittest discover -s tests -p "test_*.py"
rtk git diff --check
rtk git status --short
rtk git diff
rtk read docs/workplan.md
rtk read docs/bugs.md
rtk read docs/backlog.md
```

Если каталога `tests/` ещё нет, не маскировать это как успешный тестовый прогон:
запустить релевантные проверки изменённого кода и явно указать отсутствие общего
набора тестов. Если форматтер меняет файлы, повторить линтеры и тесты после
форматирования.

Дополнительно по области изменения:

- UI — обязательны запуск приложения, клики по сценарию и скриншоты;
- расчёты — тесты на известные входы и граничные значения;
- XLSX/шаблоны — round-trip во временном каталоге;
- обновления/сеть — тесты с mock и отдельный осторожный ручной smoke-check;
- зависимости, ресурсы или упаковка — локальная сборка:

  ```bash
  rtk bash build.sh
  ```

Коммит запрещён, если есть падающая применимая проверка, непонятный diff,
traceback при ручном сценарии или визуальный дефект. Исключение возможно только
если пользователь явно принимает известную проблему; её нужно описать в отчёте.

## 8. Правила коммита

- Перед staging ещё раз просмотреть `rtk git status --short` и `rtk git diff`.
- Добавлять только файлы текущей задачи, перечисляя их явно. Не использовать
  широкое добавление чужих изменений.
- Не коммитить `.venv`, кэши, сборочные результаты, логи, временные XLSX и
  скриншоты ручной проверки.
- Сообщение коммита должно кратко описывать результат, например:
  `Fix XLSX template round-trip` или `Add validation for Rn input`.
- Не использовать `--no-verify`, чтобы обходить проверки.
- Не делать amend, rebase, force-push или удаление чужих изменений без прямого
  указания пользователя.

Пример безопасного завершения:

```bash
rtk git add path/to/changed_file.py tests/test_changed_file.py
rtk git diff --cached
rtk git commit -m "Describe the completed change"
rtk git status --short
```

После коммита сообщить пользователю: что изменено, какие автоматические тесты и
ручные действия выполнены, где лежат скриншоты, какой commit создан и какие
проверки не удалось провести.
